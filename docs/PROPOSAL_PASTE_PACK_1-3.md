### Abstract (150–220 words; new page before Table of Contents)

Sand delivery for construction in Ghana is still arranged largely through informal networks. Clients face opaque prices, weak confirmation of bookings, little visibility of delivery status, and no structured channel for complaints. This proposal sets out the design of Tipper Truck, a cloud-connected mobile application and REST API to support sand ordering for construction clients, with a limited operator role and a web administration panel.

The proposed system will be implemented with Flutter for the Android client (the same codebase may target iOS later; demonstration will be on Android), Laravel 13 and MySQL 8 for the API, Laravel Sanctum for bearer-token authentication, and Filament for administration. Core functions to be specified and built include registration and login (email/password, with optional Google/Facebook), catalogue-driven sand and truck selection with a sand-by-truck price matrix and regional delivery surcharges, order placement, simulated Mobile Money or cash-on-delivery, status tracking by polling, order history, a server-side rule-based assistant, and issue reporting. Live GPS mapping and live MoMo/Paystack merchant processing are out of scope.

The study will use Agile development, a documented requirements set from stakeholder consultation, UML and an entity-relationship model, and automated API tests. The expected outcome is a working prototype suitable for demonstration and viva, not a commercially licensed payments product.

**Keywords:** mobile ordering; construction logistics; Flutter; Laravel; Mobile Money; Ghana

## 3. Tense and contradiction sweep

Use **will / proposes to / is to be** in Chapters 1–3. Do not write “the current version implements” in a proposal. If you have already built features, phrase them as *the design to be implemented* (the viva can show the running app).

### Sanctum (replace both broken sentences)

**Wrong:** “Unlike self-contained Sanctum tokens, Sanctum tokens are server-side records…”

**Right:**

Authentication will use Laravel Sanctum personal access tokens with a seven-day expiry. Unlike self-contained JSON Web Tokens (JWTs), Sanctum tokens are stored as server-side records, so a token can be revoked immediately on logout of that device without invalidating other devices. The Flutter client will store the token in `flutter_secure_storage` and send it as `Authorization: Bearer`.

### Operators vs GPS (Chapter 1 scope + §2.6)

**Wrong:** GPS “when the truck operator module is developed.”

**Right (scope):**

The proposed application will serve construction **clients** on Android. **Operators** (drivers) will use the same mobile application’s driver home to view assigned orders and to mark On The Way and Delivered. Operator accounts will be created by an administrator; public sign-up will create client accounts only. System administration (users, pricing, issues, catalogue) will be on the Filament web panel at `/admin`.

Live map-based GPS tracking of vehicles is **out of scope**. Tracking will mean polling order status (Confirmed → On The Way → Delivered) while the tracking screen is open, with updates expected within about ten seconds.

### iOS

**Wrong:** equal Android and iOS delivery as if both will be demonstrated.

**Right:**

Development will use Flutter so that one Dart codebase can target Android and iOS. **Implementation and examination demonstration will be on Android.** An iOS build is not required for this submission.

### Payment / PIN / “PHP API”

**Wrong:** “trust-building interface capturing account details”; leftover “PHP API” in architecture captions and §2.8.

**Right:**

Payment will be **simulated**. Clients will choose Mobile Money or cash on delivery. For MoMo the API will record network and a masked phone number and mark payment paid through a `PaymentGateway` (simulated in this project). **No Mobile Money PIN will be requested or stored.** Cash on delivery will remain pending until the order is marked delivered. Live Paystack or telco MoMo APIs remain future work.

Replace “PHP REST API” / “PHP API” in figure captions with **Laravel REST API**.
